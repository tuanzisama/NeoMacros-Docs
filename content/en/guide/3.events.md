# Events

NeoMacros scripts are event-driven: the game publishes snapshots of what is happening, and your handlers decide what to do with them. This page covers the subscription toolkit on `neo.events` and how to keep expensive events cheap.

## Subscribe with events.on

`events.on(name, handler)` registers an asynchronous listener. The handler runs on your script's event loop and receives the payload as a plain object:

```js
const { events, chat } = neo;

const handle = events.on('player:health', (payload) => {
    chat.actionbar(`health: ${payload.health}`);
});
```

Event names follow the `domain:name` convention — `chat:receive`, `player:health`, `key:press`, `world:sound`. The bare built-in `tick` is the one exception. Wildcards work too: `domain:*` matches a whole domain and `*` matches everything (high-traffic names such as `tick`, `world:sound`, and `world:blockUpdate` are excluded from wildcard dispatch by default).

To unsubscribe, pass the handle back:

```js
events.off(handle);              // by handle
events.off('player:health');     // or by event name
```

Subscriptions created while a module is loading are attributed to that module and unsubscribed automatically when it unloads.

## Let the manifest subscribe for you

An event macro declares its events under `config.event.on`, and the engine calls your exported `startup(payload)` for each occurrence — no manual wiring needed. Manual `events.on` subscriptions coexist with the declared ones and are the tool of choice for services, wildcard listeners, and subscriptions whose lifetime you control. Read [Your First Script](./first-script) for the declared style.

## Cancel events with onSync

A handful of events are cancellable — `key:press`, `chat:send`, `player:attackBlock`, `player:attackEntity`, `player:interactBlock`, and `player:interactEntity`. Only these accept synchronous subscriptions, made with `events.onSync`. The callback runs on the dispatch thread and works as a veto: return a truthy value to cancel the event, anything falsy to let it through.

```js
const { events } = neo;

events.onSync('chat:send', (payload) => {
    return payload.message.includes('secret');   // truthy vetoes the send
});
```

Sync callbacks must stay short: nothing in the game proceeds past them until they return. Decide and return — no `await`, no loops.

## Wait for a single occurrence

Three helpers cover one-shot patterns:

- `events.once(name, handler)` fires exactly once and unsubscribes itself.
- `events.waitFor(name)` returns a promise that settles with the next payload.
- `events.waitForUntil(name, filter, timeoutMillis)` resolves with the first payload matching `filter` and rejects once the timeout passes. The filter runs on the dispatch thread, so keep it cheap.

```js
const { events, chat } = neo;

try {
    await events.waitForUntil('player:health', (p) => p.health < 6, 30000);
    chat.actionbar('low health!');
} catch {
    chat.log('no low-health moment within 30s');
}
```

## Filter high-frequency events

Events like `tick` fire twenty times per second, and `world:blockUpdate` fires for every block state change the client receives. A handler that does real work on every firing will dominate your script's loop. Guard with an early return:

```js
const { events, chat } = neo;

let n = 0;

events.on('tick', () => {
    n += 1;
    if (n % 20 !== 0) return;        // bail out on 19 of every 20 ticks
    chat.actionbar('once a second');
});
```

The `tick` payload carries the tick `count`, so you can also gate on `payload.count` instead of a local counter. Whatever the guard, the body should touch as little as possible.

## Raise your own events

Scripts can publish too. `events.register('myscript:burst')` reserves a namespaced name (it cannot shadow a built-in domain), after which `events.emit('myscript:burst', payload)` delivers to other listeners on the async channel. Payload keys must avoid the reserved words `type`, `timestamp`, and `cancellable`.

Payload field tables for all built-in events live in the API: the [events facade](../api/events), [chat:receive](../api/events/chat/chat-receive), [player:health](../api/events/player/player-health), and the rest of the event catalog under it.
