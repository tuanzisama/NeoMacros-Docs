The API reference leans on a small set of recurring concepts. Each entry
below notes where the term surfaces on generated pages, so you can jump
back here whenever a chip or badge looks unfamiliar.

## Classes & values

:api-anchor{id="kind-handle"}

### Handle

A live reference to a game object. Handle getters re-query the game state
on every access, so a vanished entity reads back as `undefined` instead of
raising. Call `snapshot()` on a handle to freeze its current values into a
plain record ([Entity](./classes/entity) →
[EntitySnapshot](./classes/entitysnapshot)). Class pages mark handles with
the `Handle` chip in the declaration box (the chip links back here); other examples include
[Player](./classes/player) and [FileHandle](./classes/filehandle).

:api-anchor{id="kind-data"}

### Data

An immutable plain-data class — positions, blocks, item stacks, text.
Data values never change under you and are JSON-safe, so they can be
stored, compared, and serialized freely. Contrast with a
[handle](#kind-handle), whose reads always reflect the world right now.
Examples: [Pos2D](./classes/pos2d), [BlockPos](./classes/blockpos),
[ItemStack](./classes/itemstack), [TextComponent](./classes/textcomponent).

:api-anchor{id="kind-record"}

### Record

A plain composite type rendered as a field table — no methods, no live
state. Records mostly show up in signatures and event payloads:
[EntitySnapshot](./classes/entitysnapshot) and [Pos3d](./classes/pos3d)
are records. Class pages mark them with the `Record` chip.

## Events

:api-anchor{id="kind-event"}

### Event

A game-side occurrence your script can subscribe to through the
[events facade](./modules/core/events) (`on` / `once` / `waitFor`).
Event names are camelCase and scoped to their domain, e.g.
`player:attackBlock`. Every event page lists its payload and whether it
is cancellable; subscriptions are cleaned up automatically when the
script unloads.

### Payload

The frozen event object your handler receives — a
`…Event extends [BaseEvent](./classes/baseevent)` instance whose fields
carry the event's details. Payload fields are read-only; each payload
has its own page in the sidebar's Classes & types group, e.g.
[ChatSendEvent](./classes/chatsendevent).

### Cancellable

A badge on events that can be vetoed: returning a truthy `cancel` from
the handler stops the vanilla action (blocking a chat send, an attack,
…). Non-cancellable events fire regardless.

## Modules & exposure

### Facade module

The script-facing surface of one domain — `chat`, `world`, `hud`, … —
documented on one generated page each, grouped by category in the
sidebar's Modules tree, e.g. [chat](./modules/ui/chat). Facades are the
only way scripts touch the game; everything hangs off them.

### Global object

Every facade is exposed as `neo.<module>` on the global object, so the
simplest scripts need no imports at all — `neo.chat.log("hi")`. Every
script-facing class hangs on the same root (`neo.Entity`, `neo.Pos3D`).
Pair [`neomacros.d.ts`](https://neomacros.tuanzi.ink/neomacros.d.ts) with your editor for autocompletion.

## Availability & badges

### Availability chips

Every module and member carries three chips: **NeoMacro** (the release
that introduced it), **Minecraft** (the version availability expression
below), and **Fabric Loader**. `*` means "every one".

### MC version expression

The value behind the Minecraft chip (`@ApiMC` on the mod side): `*` for
all versions, a comparison like `>=1.20.6`, an inclusive range like
`1.18-1.21`, or an exact version. The
[version matrix](./version-matrix) evaluates every expression against
every supported build.

### Read-only

A property badge: the property observes state you cannot assign from the
script (an entity's `eyePos`, a keybind's bound key).

### Experimental

A badge warning that the member may change or disappear between
releases — usable, but not a stability promise.

### Permission

Escapes (filesystem, network, JVM interop, reflection) run behind a
trust system; a permission chip names the grant a script needs. See the
[Permissions & trust guide](../guide/permissions-trust).

## Platform background

### GraalJS

Oracle GraalVM's JavaScript engine. NeoMacros embeds it as the client's
script runtime, which is why scripts can pass values to and from real
Java objects (through the gated escapes above) while staying ordinary
JavaScript.

### Fabric

The lightweight mod loader ecosystem NeoMacros ships on. The **Fabric
Loader** chip tracks the loader build the mod was assembled against;
NeoMacros itself is a client-side Fabric mod.

### One build per Minecraft version

NeoMacros releases one jar per supported Minecraft version, because the
client internals it binds to move between releases. The mod build's
Stonecutter setup orchestrates compiling the same sources across all of
them; the [version matrix](./version-matrix) is the resulting
compatibility map.

### `neomacros.d.ts`

The TypeScript definition file mirroring the entire generated API —
drop it next to your scripts for editor autocompletion and type
checking. Download the current build from
[`/neomacros.d.ts`](https://neomacros.tuanzi.ink/neomacros.d.ts).
