---
title: "Permissions and Trust"
---

Scripts run in a sandbox. Reading world state, printing to chat, drawing overlays, and scheduling timers are always allowed — the base surface. Anything that reaches beyond it (files, network, commands, the host JVM) must be declared by the script and granted by you.

## Gated capabilities

| Permission | Unlocks |
| --- | --- |
| `fs` | Every `neo.fs` member: `readText`, `writeText`, `readJSON`, `writeJSON`, `list`, `mkdir`, `delete`, and friends |
| `net` | Every `neo.net` member: `fetch`, `get`, `post` |
| `command` | `neo.command.register` and `neo.command.execute` |
| `java` | `neo.java`, `neo.reflect`, and `neo.client.minecraft` |
| `packet` | `buffer.send()` and `buffer.toPacket()` on the packet builder face |

The first three are scoped capabilities: granting `fs` unlocks file access relative to the game directory and nothing else. The `java` permission is different — it grants full host access with no class filtering, so it amounts to the highest level of trust (see [Java Interop](./java-interop)).

## Capabilities in the manifest

A script states what it needs with the optional top-level `permissions` field:

```yaml
# config/neomacros/macros/event/backup-notes/neomacro.yml
name: backup-notes
version: 1.0.0
author: you
description: keeps a running note file
permissions: ["fs"]

config:
  event:
    on: [chat:receive]
```

Scripts with no `permissions` list (or an empty one) run entirely on the base surface and never trigger a prompt. Unknown capability names never grant anything, so a typo fails closed instead of silently widening access.

## Granting trust to a script

On first load of a script with declared capabilities, a confirmation dialog lists what was requested — the same dialog a runtime request uses, one prompt at a time (on versions without the dialog system, a clickable chat line instead). Until you decide, the script runs under a denying view — its gated calls throw. Clicking Allow grants trust; the same decision can also be made by hand, accepting either the script name or the request id:

```text
/neomacros permission allow backup-notes
```

Denying or dismissing changes nothing — no decision is persisted, and the prompt returns on the next load. Trusting applies to the running script immediately: its gated calls start working without a reload, and the script keeps its state.

Revoke removes every grant a script holds — the persisted decision, any session grant, and any session refusal — and the running script's gated calls start throwing again on their next call, no reload:

```text
/neomacros permission revoke event:backup-notes
```

Script arguments accept a `{category}:{name}` form (`event:`, `keypress:`, or `services:`), which the permission commands and `enable` / `disable` complete for you.

Trust decisions are keyed to the content hash of the script, which has two consequences:

- Editing the file changes its hash, so a trusted script can never quietly grow new capabilities — the prompt reappears, and the change is re-approved after review.
- Decisions persist across restarts (they are stored in `config.json`).

Re-approving after an edit is the normal workflow, with the prompt serving as the review step.

## What untrusted scripts cannot do

Without the matching grant, a script:

- cannot read or write any file through `neo.fs`;
- cannot open any network request through `neo.net`;
- cannot register or execute client commands;
- cannot touch `neo.java`, `neo.reflect`, or `neo.client.minecraft`.

It keeps everything on the base surface: events, timers, chat output, world and player reads, HUD and render overlays, and its own `neo.storage` store. The gated call throws when it fires, and the error shows in `/neomacros errors` — see [Troubleshooting](./troubleshooting).

## Requesting a permission at runtime

A script can query the gate and ask for a declared capability while it runs through `neo.permission`:

```js
if (!neo.permission.checkPermission('fs')) {
    const granted = await neo.permission.requestPermission('fs');
    if (!granted) {
        neo.chat.log('backup disabled: file access was denied');
        return;
    }
}
// the fs face works from here on
```

Both members accept one name or a list — a list asks (and checks) for all of it at once. `requestPermission` rejects when the manifest does not declare one of the capabilities (the declaration is the ceiling) or the name is unknown. Otherwise, an already-granted capability resolves immediately; an ungranted one pops a confirmation dialog (on versions without the dialog system, a clickable chat line instead). Allowing persists trust for the whole script — the same script-wide decision the load prompt's Allow makes — and the running script can use the capability right away, no reload. Denying or dismissing resolves `false`; the script decides how to degrade.

## Least privilege

A grant should cover only what a script actually uses, and scripts that declare less are preferable. Before trusting a script you did not write, its manifest is the first thing to read — the `permissions` line says exactly what to look for in the code. A script asking for `java` deserves a full read; one asking for nothing can be run as-is.
