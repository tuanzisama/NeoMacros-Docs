---
title: "Async and Threading"
---

Every script owns an event loop. Promises, `async`/`await`, and timers all run on that loop, which is what lets one script sleep for five seconds without touching anyone else's execution. The scheduling primitives live on `neo.thread`.

## Await time instead of blocking

The time functions return promises, so waiting never occupies the loop:

```js
const { thread, chat } = neo;

await thread.sleep(1000);    // real-time milliseconds, ignores game ticks
await thread.ticks(20);      // 20 client ticks
await thread.nextTick();     // at the end of the current tick
```

`sleep` measures wall-clock time; `ticks` and `nextTick` measure client tick boundaries. Pick ticks when the behavior should track gameplay speed, and sleep when it should track real time.

## Move work to the main thread

Minecraft keeps world and entity state on the game's main thread. Your async code runs on the script loop, which means it can wake up in the middle of a frame while the game is writing that same state. Reading or writing game state from async code is therefore a race against the client itself.

`thread.runOnMain(task)` is the bridge: it runs your function on the main thread and the promise settles with its return value. Calling it while already on the main thread executes inline.

```js
const { thread } = neo;

const health = await thread.runOnMain(() => neo.player.self?.health);
```

Rule of thumb: compute and wait on your loop, and keep every touch of game state inside `runOnMain`.

## Schedule repeating and delayed work

Four functions schedule callbacks on the script loop, and each returns a timer handle you can use to cancel:

```js
const { thread, chat } = neo;

const beat = thread.every(5000, () => chat.actionbar('still here'));
thread.after(60000, () => beat.cancel());   // stop after a minute
```

- `thread.after(millis, task)` runs once after a real-time delay.
- `thread.every(millis, task)` repeats until cancelled.
- `thread.afterTick(count, task)` and `thread.everyTick(count, task)` are the tick-boundary equivalents.

Calling `cancel()` on the returned `TimerHandle` stops any pending or future runs.

## Keep startup responsive

`startup` may be async — the promise it returns settles on your own loop, so awaiting inside it never stalls the game. What does stall things is synchronous busywork: a tight `while` loop without an `await` never yields the loop, and your own timers and event handlers queue up behind it.

For long-running work, cooperate with the loop:

```js
const { thread, chat } = neo;

export async function startup() {
    while (true) {
        await thread.ticks(40);                  // yield every 2 seconds
        chat.actionbar(`fps ${Math.round(neo.client.fps)}`);
    }
}
```

An `await` every iteration is what keeps the script responsive; reload also tears the loop down cleanly along with the module.
