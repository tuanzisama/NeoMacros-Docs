# Persistent Storage

Every script owns an isolated key-value store on `neo.storage`. It holds JSON-serializable values, survives `/neomacros reload` and full game restarts, and is keyed per script — no other script can read or write your keys.

## Write and read values

Four members cover the whole facade:

```js
const { storage } = neo;

storage.put('joined', true);            // write
const v = storage.get('joined');        // read, or null when absent
storage.has('joined');                  // exists?
storage.remove('joined');               // delete one key
```

`storage.put(key, null)` also deletes the key, and `storage.get` returns `null` for anything you have not written. The store is keyed by the script's source file, so renaming the folder keeps the data as long as the entry file name stays the same.

## Know what can be stored

Values must be plain JSON data: objects, arrays, strings, numbers, booleans — and `null` to delete. Class instances, maps, functions, and live handles do not fit. To keep a position, store its fields rather than the handle:

```js
const p = player.self.pos;
storage.put('lastPos', { x: p.x, y: p.y, z: p.z });
```

Trying to store non-serializable data is the most common storage bug; check [Troubleshooting](./troubleshooting) if `put` starts throwing.

## Keep a settings object

The classic pattern: define defaults in the script, merge whatever was saved, and write the merged object back so new default fields appear for existing users:

```js
const { storage, chat } = neo;

const DEFAULTS = { welcome: true, warnHealth: 6 };

export function startup() {
    const saved = storage.get('settings') ?? {};
    const settings = { ...DEFAULTS, ...saved };
    storage.put('settings', settings);

    if (settings.welcome) chat.log('settings loaded');
}

export function setWarning(value) {
    const saved = storage.get('settings') ?? {};
    storage.put('settings', { ...DEFAULTS, ...saved, warnHealth: value });
}
```

`storage.get('settings') ?? {}` handles the first run, where nothing has been saved yet. Spreading defaults under saved values means a saved file only needs the fields it deliberately changed.

## Track counters and cooldowns

Numbers persist just as easily. A counter grows with each occurrence:

```js
const n = (storage.get('msgCount') ?? 0) + 1;
storage.put('msgCount', n);
```

A cooldown compares timestamps — `Date.now()` works fine in scripts:

```js
const now = Date.now();
const last = storage.get('lastPing') ?? 0;

if (now - last < 5000) return;          // 5s cooldown not elapsed
storage.put('lastPing', now);
```

Keep writes where they matter: a counter bumped on every `tick` write twenty times a second, which is wasted work — accumulate in a local variable and flush periodically instead.

## Decide between storage and files

Storage is for structured state the script itself reads back: settings, counters, cooldowns, caches. It needs no permission and stays invisible to the player. When the data is meant for humans — notes, logs, an export you want to open in an editor — write a file through `neo.fs` instead; that path requires the `fs` capability and the trust that comes with it (see [Permissions and Trust](./permissions-trust)). Full signatures are on the [storage facade](../api/modules/core/storage) page.
