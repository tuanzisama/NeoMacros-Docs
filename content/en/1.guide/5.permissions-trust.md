---
title: "Permissions and Trust"
---

Scripts run in a sandbox. Reading world state, printing to chat, drawing overlays, and scheduling timers are always allowed — the base surface. Anything that reaches beyond it (files, network, commands, the host JVM) must be declared by the script and granted by you.

## Gated capabilities

| Permission | Unlocks |
| --- | --- |
| `fs` | Every `neo.fs` member: `readText`, `writeText`, `readJSON`, `writeJSON`, `list`, `mkdir`, `delete`, and friends |
| `net` | Every `neo.net` member: `fetch`, `get`, `post` |
| `command` | `neo.command.register` and `neo.command.execute` |
| `java` | `neo.java`, `neo.reflect`, and `neo.client.minecraft` |

The first three are scoped capabilities: granting `fs` unlocks file access relative to the game directory and nothing else. The `java` permission is different — it grants full host access with no class filtering, so it amounts to the highest level of trust (see [Java Interop](./java-interop)).

## Capabilities in the manifest

A script states what it needs with the optional top-level `permissions` field:

```yaml
# config/neomacros/macros/event/backup-notes/neomacro.yml
name: backup-notes
version: 1.0.0
author: you
description: keeps a running note file
permissions: ["fs"]

config:
  event:
    on: [chat:receive]
```

Scripts with no `permissions` list (or an empty one) run entirely on the base surface and never trigger a prompt. Unknown capability names are rejected by the trust gate, so a typo fails closed instead of silently widening access.

## Granting trust to a script

On first load of a script with declared capabilities, a chat prompt lists what was requested. Until you decide, the script runs under a denying view — its gated calls throw. Clicking the prompt runs the command for you; the same command can also be typed by hand:

```text
/neomacros trust backup-notes
```

Trust decisions are keyed to the content hash of the script, which has two consequences:

- Editing the file changes its hash, so a trusted script can never quietly grow new capabilities — the prompt reappears, and the change is re-approved after review.
- Decisions persist across restarts (they are stored in `config.json`).

Re-approving after an edit is the normal workflow, with the prompt serving as the review step.

## What untrusted scripts cannot do

Without the matching grant, a script:

- cannot read or write any file through `neo.fs`;
- cannot open any network request through `neo.net`;
- cannot register or execute client commands;
- cannot touch `neo.java`, `neo.reflect`, or `neo.client.minecraft`.

It keeps everything on the base surface: events, timers, chat output, world and player reads, HUD and render overlays, and its own `neo.storage` store. The gated call throws when it fires, and the error shows in `/neomacros errors` — see [Troubleshooting](./troubleshooting).

## Least privilege

A grant should cover only what a script actually uses, and scripts that declare less are preferable. Before trusting a script you did not write, its manifest is the first thing to read — the `permissions` line says exactly what to look for in the code. A script asking for `java` deserves a full read; one asking for nothing can be run as-is.
