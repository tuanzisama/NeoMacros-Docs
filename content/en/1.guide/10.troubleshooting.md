---
title: "Troubleshooting"
---

Scripts fail in repeatable ways. This page maps the common failure modes to their causes and gives a checklist to run through before asking for help.

## Read the errors screen

`/neomacros errors` opens the screen listing recent script failures — invalid folders and runtime exceptions alike — with the script name, message, and stack trace pointing back to your file. A thrown error never takes the game down: NeoMacros captures it, skips the failing handler, and keeps your other scripts running.

## Diagnose ungranted capability errors

An error about a denied call means the script touched something behind the trust gate — `fs`, `net`, `command`, or `java` — without a grant. Re-check the manifest: does the `permissions` list declare what the code actually calls? Then approve it:

```text
/neomacros trust <script>
```

Remember that editing the script changes its content hash, so trust must be re-granted after changes — a previously working script failing this way right after an edit is almost always that.

## Fix manifest validation failures

A folder that never appears in `/neomacros list` was rejected at load. The usual culprits:

- **A typo'd event name** in `config.event.on`. Event names are validated against the catalog at load; an unknown name is rejected with the list of available events. Copy names exactly from the event pages, casing included — several names are camelCase, such as `world:blockUpdate` and `player:attackBlock`.
- **A missing `domain:` prefix.** Nearly all events are named `domain:name` (`chat:receive`, `player:health`). Writing `receive` instead of `chat:receive` fails validation. The bare `tick` is the only built-in without a domain.
- **Legacy top-level behavior fields.** `key`, `lifecycle`, `autostart`, and `events` at the manifest top level are gone; behavior lives in the `config:` block now, and loading old manifests fails with a migration error naming the target.
- **Missing required identity fields** — `name`, `version`, and `author` must all be present.

## Avoid lifecycle races and stale reads

Live handles read current state, which has a consequence: outside a world, `player.self` reads `undefined`, and entity handles whose entity vanished read back as `undefined` too. A script that assumed a world — a service with `lifecycle: always`, or an async loop still running after leaving — crashes on the first property read. Guard the reads:

```js
const p = player.self;
if (!p) return;
```

The same guard matters after dimension changes or respawns, where a previously valid handle can briefly point at nothing.

## Do not block the script loop

A handler that never awaits — a tight polling loop, a long computation — monopolizes the script's event loop, and everything else (timers, event delivery) queues behind it. Every long wait should be an `await thread.sleep(...)`, `thread.ticks(...)`, or `thread.nextTick()`; see [Async and Threading](./async-threading). Touching game state from async code belongs inside `thread.runOnMain`.

## Store only serializable data

`storage.put` accepts plain JSON data. Passing a live handle, a class instance, or a function fails; `null` is special and deletes the key. If a `put` call throws, inspect the value with `JSON.stringify` — what survives that round-trip is what the store accepts.

## Run the checklist

When something misbehaves, work down this list:

1. `/neomacros list` — does the script appear at all? No: it is a manifest problem, check the rejection reason in `/neomacros errors`.
2. `/neomacros errors` — read the newest entry's message and stack trace; the file and line are usually enough.
3. Does the manifest declare every capability the code calls, and was the script re-trusted after the last edit?
4. Are event names spelled exactly as the catalog spells them, domain prefix included?
5. Does the handler guard `player.self` and entity handles against `undefined`?
6. Does every loop yield with an `await`, and is game state only touched on the main thread?
7. Still stuck? Reduce the script to the smallest part that fails, then compare your call signatures against the [API reference](../api/overview).
