# 异步与线程

每个脚本拥有一个事件循环。promise、`async`/`await` 和定时器都在这个循环上运行——这正是让一个脚本睡上五秒也不会碰及其他脚本执行的原因。调度原语都在 `neo.thread` 上。

## 用 await 等待，而不是阻塞

时间类函数返回 promise，因此等待永远不会占用循环：

```js
const { thread, chat } = neo;

await thread.sleep(1000);    // real-time milliseconds, ignores game ticks
await thread.ticks(20);      // 20 client ticks
await thread.nextTick();     // at the end of the current tick
```

`sleep` 以墙钟时间计时；`ticks` 和 `nextTick` 以客户端 tick 边界计时。行为要跟随游戏节奏就用 tick，要跟随现实时间就用 sleep。

## 把工作挪到主线程

Minecraft 把世界和实体状态保存在游戏的主线程上。你的异步代码运行在脚本循环上，这意味着它可能在游戏正在写入同一份状态时、在帧的中间被唤醒。因此，从异步代码读写游戏状态，等于在和客户端本身赛跑。

`thread.runOnMain(task)` 就是那座桥：它把你的函数放到主线程上执行，promise 以其返回值结算。如果调用时已经在主线程上，则直接内联执行。

```js
const { thread } = neo;

const health = await thread.runOnMain(() => neo.player.self?.health);
```

经验法则：计算和等待都在自己的循环上进行，对游戏状态的每一次触碰都放进 `runOnMain`。

## 调度重复与延迟任务

四个函数在脚本循环上调度回调，每个都返回可用于取消的定时器句柄：

```js
const { thread, chat } = neo;

const beat = thread.every(5000, () => chat.actionbar('still here'));
thread.after(60000, () => beat.cancel());   // stop after a minute
```

- `thread.after(millis, task)` 在一段现实时间的延迟后运行一次。
- `thread.every(millis, task)` 反复运行，直到被取消。
- `thread.afterTick(count, task)` 和 `thread.everyTick(count, task)` 是 tick 边界版本的等价物。

对返回的 `TimerHandle` 调用 `cancel()`，会终止所有挂起的和未来的运行。

## 保持 startup 响应

`startup` 可以是 async 的——它返回的 promise 在你自己的循环上结算，因此在其中 await 永远不会卡住游戏。真正会造成卡顿的是同步的忙活：一个没有 `await` 的紧凑 `while` 循环从不让出循环，你自己的定时器和事件处理器只能在它后面排队。

对于长时间运行的工作，请与循环合作：

```js
const { thread, chat } = neo;

export async function startup() {
    while (true) {
        await thread.ticks(40);                  // yield every 2 seconds
        chat.actionbar(`fps ${Math.round(neo.client.fps)}`);
    }
}
```

每轮迭代里的一个 `await` 就是脚本保持响应的关键；重载时这个循环也会连同模块一起被干净地拆除。订阅见[事件系统](./modules/core/events)，持久化这些循环产出的数据见[存储与状态](./modules/core/storage)。完整的原语列表见 [thread 门面](../api/modules/core/thread)页。
